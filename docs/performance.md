# Performance notes

Generated by `benchmarks/benchmark.py` on a local machine (Spark `local[*]`), using the silver encounters
table copied 500 times: **3,381,000 rows**. Each timing is the best of 3 runs, in seconds. Absolute numbers
depend on the laptop; the ratios are the point.

| Experiment | Baseline | Optimised | Optimised is |
|---|---|---|---|
| File format (group-by on cost) | CSV with schema inference: 1.62s | Parquet: 0.09s | 18.5x faster |
| Filter `year = 2021` | Unpartitioned parquet: 0.04s, reads 16 files / 114.2 MB | Partitioned by year: 0.03s, reads 1 file / 1.8 MB | 1.6x faster |
| Join fact to `dim_patient` | Sort-merge join (shuffle both sides): 0.39s | Broadcast hash join: 0.23s | 1.7x faster |

## Why

- **Parquet vs CSV**: parquet is columnar and typed. Spark reads only the 2 columns the query needs and skips
  parsing text; CSV must be read in full and, with `inferSchema`, read twice.
- **Partition pruning**: with `partitionBy("year")` each year is its own folder. Spark turns the filter into
  a `PartitionFilters` entry in the plan and never opens the other folders, so it reads far less data
  (see the MB column). At this small size the time saved is tiny; the data saved is what grows with scale.
  Partition-folder listing is excluded from the timing, as a Hive metastore keeps the partition list:
  `PartitionFilters: [isnotnull(year#610), (year#610 = 2021)]`
- **Broadcast join**: `dim_patient` is tiny, so Spark ships a copy to every executor and joins locally
  instead of shuffling both tables by `patient_id`. Plan uses SortMergeJoin when broadcast is disabled:
  True; BroadcastHashJoin with `F.broadcast`: True.
